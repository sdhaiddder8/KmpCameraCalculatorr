# KMP Calculator + Camera


A small Kotlin Multiplatform app: a calculator screen with native camera capture on
Android and iOS. Calculation, validation and the MVI state all live in `commonMain`;
the platforms only render state and dispatch events.

## Structure

```
shared/
  commonMain/
    model/       MathOperation, CalculatorState, PhotoStatus, PhotoReference
    validation/  InputValidator, CalculatorErrors
    calculation/ Calculator
    mvi/         CalculatorIntent, CalculatorEffect, CalculatorReducer,
                 CalculatorStore, CalculatorComponent
    camera/      CameraController, CameraCaptureResult
  commonTest/    the shared tests
  iosMain/       createCalculatorComponent(camera) factory for Swift
androidApp/      Jetpack Compose
iosApp/          SwiftUI  (xcodeproj generated by iosApp/project.rb)
```

### What's shared vs native

`commonMain` owns the state, the reducer, all validation and error strings, the
arithmetic, and the camera intent/effect. It never sees `Bitmap`, `Uri` or `UIImage`.

The platforms register their camera launchers, request permissions, run the real
`UIImagePickerController` / `ACTION_IMAGE_CAPTURE`, and decode the file path in
`PhotoReference` into an image for display.

### MVI

- `CalculatorState` is a single immutable `data class`.
- The only way to change it is `CalculatorStore.dispatch(intent)`, which runs
  `CalculatorReducer.reduce(state, intent)` — a pure function.
- `state` is a read-only `StateFlow`. One-off effects (`LaunchCamera`, `ReleasePhoto`)
  go on a separate `Channel`-backed `Flow` so each is delivered once.

`OpenCameraClicked` produces exactly one `LaunchCamera`. The platform runs the camera
and dispatches the result back as `PhotoCaptured` / `PhotoCaptureCancelled` /
`CameraPermissionDenied` / `CameraUnavailable` / `PhotoCaptureFailed`.

There are no view-models. `CalculatorStoreHolder` (an Android `ViewModel`, for
config-change survival) and `CalculatorViewStore` (a SwiftUI `ObservableObject`) are
thin platform holders — they own the shared store, expose its `state`/`effects`, and
forward `dispatch`. No state or logic lives in them; the text fields dispatch intents
rather than writing back into a mutable property.

### Photo files

`PhotoReference` is just a file path plus size and timestamp. Files go in the app's
cache dir (`cacheDir/photos` on Android, `Caches/photos` on iOS). When a photo replaces
another, the reducer emits `ReleasePhoto` with the old reference and the platform
deletes that file. Cancelling or failing keeps whatever photo was there.

### iOS Simulator

There's no camera on the Simulator, so `IosCameraController` builds in a fake for the
Simulator target only (`#if targetEnvironment(simulator)`) that generates a labelled
image and returns it as a normal capture. The real `UIImagePickerController` path runs
on a device.

## Running

Needs JDK 17, Android SDK (API 35), Xcode 16+. Put `sdk.dir=...` in `local.properties`
or set `ANDROID_HOME`.

Android:

```
./gradlew :androidApp:installDebug
```

iOS:

```
cd iosApp
gem install xcodeproj      # once
ruby project.rb            # regenerates iosApp.xcodeproj
open iosApp.xcodeproj
```

Run the `iosApp` scheme. A build phase runs `:shared:embedAndSignAppleFrameworkForXcode`,
so the framework builds automatically. The project uses ad-hoc signing, so it runs on
the Simulator without an Apple account; set a team for a device.

Tests:

```
./gradlew :shared:allTests
```

tests covering the four operations, negatives and decimals, whitespace, the
validation messages (reported together), divide by zero incl. `-0`, overflow, state
changes per intent, result/error clearing, the single camera effect, every camera
result, replaced-photo cleanup, and inputs not wiping a captured photo. They run the
real store; the arithmetic isn't re-implemented in the tests.

## Notes

- Number type is `Double`. Whole results print as `5`; decimals stay as
  they are. Results past `1e15` (or non-finite) are rejected as "Result is too large".
- Android declares `CAMERA` and requests it at runtime. `ACTION_IMAGE_CAPTURE` doesn't
  strictly need the permission, but declaring it is what makes the "Camera permission is
  required" path real and testable. `android.hardware.camera.any` is `required="false"`
  so the app still installs without a camera; availability is checked at runtime.
- The iOS Simulator has no camera, so `IosCameraController` compiles a fake for the
  Simulator target only (`#if targetEnvironment(simulator)`); the real
  `UIImagePickerController` path is always compiled and used on device. `CameraController`
  is also an injectable seam, so a fake can be passed in from the app or a test.
- Android can't tell a camera cancel from a rare capture failure via
  `ACTION_IMAGE_CAPTURE`, so it treats "not saved" as a cancel. The failure path is
  still modelled and is reachable on iOS.
- `Double.toString()` can differ in the last digit between JVM and Native for some
  repeating decimals.
- Decimal keyboards are used where they exist (`KeyboardType.Decimal` / `.numbersAndPunctuation`),
  but validation never relies on the keyboard — it parses and range-checks the text.
- The operation labels ("Addition", "Subtraction"…) are the only per-platform strings;
  the glyph (`+ − × ÷`) lives on the shared `MathOperation` enum.
- Libraries: kotlinx-coroutines (state + effects), AndroidX Compose / Activity /
  Lifecycle, androidx.exifinterface (photo rotation), and the `xcodeproj` Ruby gem
  (dev only, to generate the Xcode project). No DI, networking or image-loading libs.
